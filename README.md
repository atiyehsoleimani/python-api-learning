# Python API Learning Project

A FastAPI learning project focused on professional backend architecture: a small REST API for **users** and their **posts**, built in layers with migrations, configuration management and tests.

## Goals

- Understand Python package design and encapsulation
- Master dependency injection and layered architecture
- Build production-quality patterns: exception hierarchy, configuration, migrations, testing

## Tech Stack

FastAPI, Pydantic v2, SQLAlchemy 2.0, Alembic, pydantic-settings, pytest. Developed with Python 3.12.

## Architecture

```
app/
├── main.py              # Application entry point (no startup side effects)
├── config.py            # Settings loaded from environment variables / .env
├── database.py          # Engine and session factory
├── dependencies.py      # get_db dependency
├── routes/              # HTTP layer (APIRouter), registered in registry.py
├── services/            # Business logic, receive a db Session
├── models/              # SQLAlchemy ORM models (User, Post)
├── schemas/             # Pydantic request/response schemas
└── exceptions/          # Exception hierarchy and a generic handler
alembic/                 # Database migrations
tests/                   # pytest tests
```

Request flow: **Route -> Service -> ORM model -> Database**. Each layer has one job: routes handle HTTP, services hold the logic, models map tables, schemas define the API contract.

## Principles Applied

- **Separation of concerns**: routes do not touch the database; services do not know about HTTP.
- **Dependency injection**: routes get the DB session through `Depends(get_db)`; services receive it as an argument. Tests replace it with a test database via `app.dependency_overrides`.
- **Open/Closed**: a new `NotFoundException` subclass needs no changes to the exception registry; one generic handler covers all `AppException` subclasses.
- **Schema as code**: Alembic owns the database schema. The app never creates tables at startup.
- **12-factor configuration**: settings come from environment variables (`.env`), with one source of truth in `app/config.py`.

## Getting Started

```bash
# 1. Create and activate a virtual environment
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

# 2. Install dependencies
pip install -r requirements.txt

# 3. Configure environment
cp .env.example .env             # then edit the values

# 4. Create the database tables
alembic upgrade head

# 5. Run the API
uvicorn app.main:app --reload
```

Interactive API docs: http://127.0.0.1:8000/docs

### Configuration

| Variable | Description | Example |
|---|---|---|
| `DATABASE_URL` | SQLAlchemy database URL | `sqlite:///users.db` |
| `SECRET_KEY` | Secret key (not used yet; reserved for authentication) | `change-me` |
| `DEBUG` | Debug flag | `false` |

`.env` is git-ignored. `.env.example` documents the available settings.

## API Endpoints

### Users

| Method | Path | Description | Success |
|---|---|---|---|
| GET | `/users` | List users | 200 |
| POST | `/users` | Create a user | 201 |
| GET | `/users/{user_id}` | Get one user | 200 |
| PUT | `/users/{user_id}` | Replace a user | 200 |
| DELETE | `/users/{user_id}` | Delete a user | 200 |

### Posts

| Method | Path | Description | Success |
|---|---|---|---|
| GET | `/users/{user_id}/posts?skip=0&limit=100` | List a user's posts (paginated, `limit` 1-100) | 200 |
| POST | `/users/{user_id}/posts` | Create a post for a user | 201 |
| GET | `/posts/{post_id}` | Get one post | 200 |
| PATCH | `/posts/{post_id}` | Partially update a post | 200 |
| DELETE | `/posts/{post_id}` | Delete a post | 200 |

Path IDs must be greater than 0 (otherwise `422`). A missing user or post returns `404` with `{"detail": "<message>"}`. A post title must be at least 1 character.

Design note: posts are addressed under `/users/{user_id}/posts` when the owner matters (list, create) and under `/posts/{post_id}` when the post's own identity is enough.

## Database Migrations

```bash
alembic upgrade head                                   # apply all migrations
alembic revision --autogenerate -m "describe change"   # create a migration after changing a model
alembic downgrade -1                                   # undo the last migration
```

Always review an autogenerated migration before applying it.

## Running Tests

```bash
pytest
```

Tests use FastAPI's `TestClient` with an in-memory SQLite database. The database dependency is replaced through `app.dependency_overrides[get_db]`, and `StaticPool` keeps one shared connection so the in-memory database is visible to all sessions. Tables are created with `Base.metadata.create_all()` in tests; Alembic handles real environments.

## Known Limitations / Roadmap

- No tests for the posts endpoints yet.
- Tests share one database and are not isolated from each other (no per-test rollback).
- Whitespace-only titles (`"  "`) are still accepted; the `posts.title` column is nullable in the database (only the schema rejects empty titles).
- Planned: authentication and authorization, logging, async database access, Docker.
